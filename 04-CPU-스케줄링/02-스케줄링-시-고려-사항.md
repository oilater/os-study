# 2. 스케줄링 시 고려 사항

CPU 스케줄러가 어떤 프로세스에 CPU를 먼저 줄지 정할 때 고려해야 할 사항들을 살펴본다.

## 2.1 선점형 스케줄링과 비선점형 스케줄링

'선점'은 빼앗을 수 있다는 뜻이고, '비선점'은 빼앗을 수 없다는 뜻이다.

> [!IMPORTANT]
> - **선점형 스케줄링 (preemptive scheduling)**: 프로세스가 CPU를 받아 실행 중이더라도 운영체제가 CPU를 강제로 빼앗을 수 있는 방식
> - **비선점형 스케줄링 (non-preemptive scheduling)**: 프로세스가 CPU를 점유하면 다른 프로세스가 빼앗을 수 없는 방식

### 선점형 스케줄링

- 운영체제가 필요하다고 판단하면 실행 중인 작업을 중단시키고 새 작업을 시작할 수 있다.
- 대표적인 예가 **인터럽트 처리**다. CPU가 인터럽트를 받으면 하던 작업을 멈추고 커널이 인터럽트를 처리한 뒤, 원래 작업으로 돌아간다.
- 문맥 교환 같은 부가 작업 때문에 낭비가 생긴다.
- 하지만 한 프로세스가 CPU를 독점할 수 없어, 빠른 응답이 필요한 **대화형 시스템이나 시분할 시스템**에 적합하다.
- 대부분의 저수준 스케줄러는 선점형을 쓴다.

### 비선점형 스케줄링

- 프로세스가 실행 상태에 들어가면 **종료되거나 스스로 대기 상태에 들어갈 때까지** 계속 실행된다.
- 스케줄러의 작업량이 적고 문맥 교환에 의한 낭비도 적다.
- 하지만 CPU를 오래 쓰는 프로세스 때문에 짧은 프로세스 여러 개가 오래 기다려, 전체 처리율이 떨어진다.
- 과거의 일괄 작업 시스템에서 쓰던 방식이다.

### 선점형과 비선점형이 섞여 있을 때

- 선점형 스케줄러에도 비선점형 프로세스가 있을 수 있다. 예: 시스템 백업 프로세스
- 이때는 비선점형 프로세스의 중요도를 아주 낮게 설정해, 선점형 프로세스에 영향을 덜 주게 한다.

| 구분 | 선점형 | 비선점형 |
| --- | --- | --- |
| 작업 방식 | 실행 중인 작업을 중단시키고 새 작업을 실행할 수 있다 | 실행 중인 작업이 끝날 때까지 다른 작업을 할 수 없다 |
| 장점 | CPU를 독점할 수 없어 대화형·시분할 시스템에 적합하다 | 스케줄러의 작업량과 문맥 교환 오버헤드가 적다 |
| 단점 | 문맥 교환 오버헤드가 많다 | 기다리는 프로세스가 많아 처리율이 떨어진다 |
| 사용 | 시분할 방식 스케줄러 | 일괄 작업 방식 스케줄러 |
| 중요도 | 높다 | 낮다 |

## 2.2 프로세스 우선순위

### 우선순위가 없다면

- 모든 프로세스의 중요도가 같다는 뜻이다.
- 준비 상태에 한 줄로 서서 순서대로 실행된다. 준비 큐가 하나인 것과 같다.
- 비유: 꽉 찬 레스토랑에서 도착한 순서대로 자리를 받는 손님들

### 우선순위가 있다면

- 대부분의 CPU 스케줄러는 우선순위를 쓴다. 프로세스마다 중요도가 다르다는 뜻이다.
- 비유: 예약 손님은 일반 손님보다 우선순위가 높다. 예약했는데도 줄을 서야 한다면 예약할 이유가 없다.
- 우선순위가 높다는 것은 **더 빨리, 더 자주 실행된다**는 뜻이다.

**커널 프로세스 vs 일반 프로세스**

- 커널 프로세스의 우선순위가 일반 프로세스보다 높다. 같게 처리하면 커널의 중요한 작업이 제대로 이루어지지 않는다.
- 같은 커널 프로세스끼리도 더 중요한 쪽이 우선순위가 높다.

**일반 프로세스끼리도 다르다**

| 프로세스 | 우선순위 | 이유 |
| --- | --- | --- |
| 워드프로세서 | 낮음 | 사람의 타이핑 속도가 CPU보다 훨씬 느려서, 천천히 실행돼도 입력을 처리할 수 있다 |
| 비디오 플레이어 | 높음 | 실시간으로 데이터를 읽어 영상과 소리를 내야 해서, 자주 실행되지 않으면 화면이 끊긴다 |

### 사용자가 우선순위를 조절하기

- 유닉스에서는 `nice` 명령어로 우선순위를 조절한다.
  - **관리자 (administrator)만 우선순위를 높일 수 있고**, 일반 계정은 낮추는 것만 가능하다.
- 윈도우에서는 작업 관리자나 프로그램 설정에서 조절한다. 예: PotPlayer의 재생 설정 > 작업 우선권

| PotPlayer 작업 우선권 | 설명 |
| --- | --- |
| 보통 이하 | 낮음과 보통 사이 |
| 보통 | 기본 우선권 |
| 보통 이상 (권장) | 보통과 높음 사이 |
| 높음 | 보통보다 끊김이 줄어들 수 있음 |
| 실시간 | 문제가 생길 수 있으니 사용하면 안 됨 |

- 우선순위를 조절하면 **다른 프로세스의 실행 속도에도 영향**을 준다.
  - 비디오 플레이어의 우선순위를 너무 높이면 CPU를 거의 비디오 플레이어만 써서 다른 작업이 원활하지 않다.
  - 그래서 유닉스에서는 우선순위를 높이는 권한을 관리자에게만 준다.
- 반대로 일부러 낮춰야 할 때도 있다.
  - 예: 워드프로세서, 비디오 플레이어, 대용량 파일 압축, 디스크 백업이 함께 돌아 느리다면, 천천히 해도 되는 **압축과 백업의 우선순위를 낮춰** 다른 작업을 빨리 할 수 있다.

결론적으로 시스템에는 다양한 우선순위의 프로세스가 공존하며, 우선순위가 높은 프로세스가 CPU를 먼저, 더 오래 차지한다.

> [!NOTE]
> 시스템에 따라 높은 숫자가 높은 우선순위일 수도, 낮은 숫자가 높은 우선순위일 수도 있다. 이 책에서는 **낮은 숫자가 높은 우선순위**다. 즉 0번이 가장 높다.

> [!TIP]
> **nice 값**
>
> 리눅스의 nice 값은 -20 ~ 19이고, 이 책과 마찬가지로 **값이 낮을수록 우선순위가 높다.** "nice"라는 이름처럼 값을 올리면 다른 프로세스에게 양보하는 착한 프로세스가 된다.
>
> ```sh
> nice -n 10 tar czf backup.tar.gz ~/data   # 우선순위를 낮춰서 실행
> renice -n 5 -p 1234                       # 실행 중인 프로세스(PID 1234)의 nice 값 변경
> sudo renice -n -5 -p 1234                 # 우선순위를 높이려면 관리자 권한이 필요
> ```

## 2.3 CPU 집중 프로세스와 입출력 집중 프로세스

프로세스가 실제로 작업하는 것은 **실행 상태**와 **대기 상태**다. (준비 상태는 CPU를 기다리기만 한다.)

| 작업 | 의미 |
| --- | --- |
| CPU 버스트 (CPU burst) | CPU를 할당받아 실행하는 작업 |
| 입출력 버스트 (I/O burst) | 입출력을 요청하고 완료될 때까지 기다리는 작업 |

```mermaid
flowchart LR
    C1["CPU 버스트"] --> I1["입출력 버스트"] --> C2["CPU 버스트"] --> I2["입출력 버스트"] --> C3["CPU 버스트"]
```

어떤 버스트가 많으냐에 따라 프로세스를 둘로 나눈다.

| 구분 | 의미 | 예 |
| --- | --- | --- |
| CPU 집중 프로세스 (CPU bound process) | CPU 버스트가 많은 프로세스 | 수학 연산 |
| 입출력 집중 프로세스 (I/O bound process) | 입출력 버스트가 많은 프로세스 | 저장장치에서 데이터 복사 |

### 입출력 집중 프로세스를 먼저

둘이 함께 있을 때는 **입출력 집중 프로세스를 먼저 실행**하는 것이 효율적이다.

- 입출력 집중 프로세스는 CPU를 잠깐 쓰고 곧 입출력을 요청해 대기 상태로 간다. 그동안 다른 프로세스가 CPU를 쓸 수 있다.
- 반대로 CPU 집중 프로세스가 먼저 들어가면 타임 슬라이스를 다 쓸 때까지 다른 프로세스가 실행되지 못한다.

```
(a) CPU 집중 프로세스 우선 배정
CPU    | CPU 집중 ██████████ | 입출력 집중 ██ |
입출력  |                     |               | 입출력 집중 ████ |
        → 입출력 장치가 앞부분 내내 놀고 있다

(b) 입출력 집중 프로세스 우선 배정
CPU    | 입출력 집중 ██ | CPU 집중 ██████████ |
입출력  |               | 입출력 집중 ████     |
        → CPU와 입출력이 동시에 일한다
```

- 그래서 스케줄링 시 입출력 집중 프로세스의 우선순위를 CPU 집중 프로세스보다 높이면 시스템 효율이 올라간다.
- 책에서는 입출력 집중 프로세스가 CPU 집중 프로세스보다 먼저 실행 상태에 들어가는 것을 **사이클 훔치기 (cycle stealing)** 라고 부른다.

> [!NOTE]
> 일반적으로 사이클 훔치기는 **DMA 컨트롤러가 CPU 대신 메모리 버스를 잠깐씩 빌려 쓰는 것**을 가리키는 용어다. 다른 책이나 자료에서는 이 뜻으로 더 많이 쓰이니 헷갈리지 않도록 주의하자.

## 2.4 전면 프로세스와 후면 프로세스

워드프로세서를 쓰면서 큰 파일을 압축한다고 해 보자.

- 워드프로세서는 키보드 입력을 받아야 하므로 **전면 프로세스**로 실행된다.
- 압축 프로그램은 끝날 때까지 입력이 필요 없으므로 **후면 프로세스**로 실행된다.

| 구분 | 의미 | 다른 이름 |
| --- | --- | --- |
| 전면 프로세스 (foreground process) | GUI 운영체제에서 화면 맨 앞에 놓인 프로세스. 현재 입출력을 사용하며 사용자와 상호작용한다 | 상호작용 프로세스 |
| 후면 프로세스 (background process) | 사용자와 상호작용이 없는 프로세스. 입력 없이 작동한다 | 일괄 작업 프로세스 |

- 예: 윈도우에서 웹 브라우저와 아래아한글이 실행 중일 때, 키보드와 화면에 대한 허가를 받은 맨 앞의 웹 브라우저가 전면 프로세스다. 작업 표시줄의 아이콘을 클릭해 전환한다.
- 전면 프로세스는 사용자 요구에 즉각 반응해야 하므로 **우선순위가 후면 프로세스보다 높다.**
- 그만큼 후면 프로세스는 CPU를 받을 확률이 낮다.

## 2.5 정리

| 우선순위 높음 | | 우선순위 낮음 |
| --- | :---: | --- |
| 커널 프로세스 | ↔ | 일반 프로세스 |
| 전면 프로세스 | ↔ | 후면 프로세스 |
| 대화형 프로세스 | ↔ | 일괄 처리 프로세스 |
| 입출력 집중 프로세스 | ↔ | CPU 집중 프로세스 |

- **커널 / 일반**, **전면 / 후면**은 분명하게 구분할 수 있어서 우선순위 배정 기준으로 쓴다.
- **대화형 / 일괄 작업**, **입출력 집중 / CPU 집중**은 프로세스에 따라 명확히 구분하기 어려울 때가 있어서, 우선순위에 반영하기 어려울 수 있다.

> [!TIP]
> **실제 운영체제는 어떻게 구분할까?**
>
> 프로세스가 입출력 집중인지 미리 알 수 없으니, 실행하면서 **행동을 보고 판단**한다.
>
> - 리눅스 스케줄러는 프로세스가 CPU를 쓴 시간을 기록하고, 적게 쓴 프로세스에게 먼저 CPU를 준다. 입출력 대기로 자주 잠드는 프로세스는 CPU 사용 시간이 적어 자연스럽게 앞쪽으로 온다.
> - 윈도우는 입출력이 끝나 깨어난 스레드나 전면 창의 스레드에 잠깐 우선순위를 올려 주는 **priority boost**를 쓴다.
